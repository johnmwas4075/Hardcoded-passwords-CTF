# Hardcoded Passwords

## Overview

This challenge focused on identifying hardcoded authentication credentials within a client-side JavaScript file. The website provided a login form, and authentication was handled using JavaScript loaded by the browser.

By inspecting the login process through the browser's Developer Tools, I identified a file named `secure.js`. Reviewing the file revealed a hardcoded username and password, which I used to authenticate successfully and retrieve the flag.

The challenge demonstrates the risks of implementing authentication logic and storing sensitive credentials in client-side code.

## Initial Reconnaissance

I accessed the challenge website and observed a login form that required a username and password.

I initially submitted incorrect credentials to observe how the application processed the login attempt.

Since the login attempt did not succeed, I investigated the authentication process using the browser's Developer Tools.

## Inspecting Network Requests

I opened the browser's Developer Tools and navigated to the **Network** panel.

I submitted another login attempt and monitored the requests generated by the application. During this process, I identified a JavaScript file named:

```text
secure.js
```

The file appeared to be involved in the website's client-side authentication process.

## Analyzing the JavaScript File

I opened `secure.js` to inspect its contents.

The file contained hardcoded login credentials, including the username and password used by the application to validate authentication attempts.

Because JavaScript files delivered to a browser can be viewed by users, these credentials were exposed to anyone who inspected the application's client-side resources.

This revealed a significant security weakness: sensitive authentication information was stored directly in client-side code rather than being securely managed on the server.

## Exploitation

After identifying the hardcoded credentials, I returned to the login page and entered the discovered username and password.

The application accepted the credentials and granted access to the authenticated area, where I retrieved the challenge flag.

## Vulnerability Analysis

**Vulnerability:** Hardcoded credentials in client-side JavaScript.

**Root cause:** The application stored authentication credentials directly in a JavaScript file delivered to the browser.

**Security impact:**

* **Credential disclosure:** Anyone could inspect the JavaScript source and discover the embedded credentials.
* **Authentication bypass:** An attacker could use the exposed credentials to gain access to the application.
* **Unauthorized access:** If the credentials protected sensitive functionality or were reused elsewhere, the impact could extend beyond the challenge.
* **False security assumptions:** Obscuring a JavaScript filename or relying on client-side checks does not protect authentication secrets.

Client-side JavaScript is accessible to the user and must therefore be treated as public. Naming a file `secure.js` does not make its contents secure.

## Security Lessons Learned

1. **Never hardcode passwords in client-side code.** Credentials embedded in JavaScript can be recovered through browser Developer Tools or direct file requests.
2. **Perform authentication on the server.** The server must validate submitted credentials before granting access.
3. **Protect secrets appropriately.** Store sensitive configuration and credentials in secure server-side configuration or a secrets manager.
4. **Do not rely on client-side validation for authorization.** Client-side checks can be inspected, modified, or bypassed.
5. **Use proper password storage.** Applications should store passwords using a suitable salted password-hashing algorithm rather than plaintext passwords.
6. **Review exposed assets.** JavaScript files, source maps, API responses, and other publicly accessible resources should not disclose secrets.

## Conclusion

This challenge demonstrated how hardcoded credentials in client-side JavaScript can compromise an application's authentication mechanism.

### The key lesson is that anything delivered to the browser should be considered accessible to the user. Authentication and authorization must be enforced on the server, and sensitive credentials must never be embedded in publicly accessible JavaScript files.
